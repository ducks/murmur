# Bounded research workflow for agents

The coordinator executes a declared comparison. It does not generate a hypothesis, inspect scientific literature, modify model code, or make a scientific judgment. An agent or researcher performs those tasks and remains responsible for every claim.

1. **Choose a question.** Review `RESEARCH.md`, `EXPERIMENTS.md`, and the relevant runner. State the mechanism, what it predicts, and a result that would count against it. Check established literature when making novelty claims.
2. **Make a plan before looking at new results.** Create a versioned JSON manifest and configs. Declare the candidate, baseline, controls, metrics, target condition, measurable thresholds, and budgets. Explain controls' extra information or resources. Pick fresh seed groups and check role offsets, not just top-level seeds. A new model requires code and a registered adapter; the coordinator supports `unlabeled_context`, `candidate_context`, and `milestone_context`.
3. **Validate and commit.** Add meaningful model, causality and leakage tests; run the relevant tests in the Nix shell. Commit the plan, configs and implementation before preparing if a reconstructible revision is required. The coordinator fingerprints dirty work but does not archive it.
4. **Prepare the plan.** Run `prepare` into a new ignored directory. It copies and hashes plan/configs and captures HEAD, working-tree status and tool versions. `next` tells you the bounded next step; `cycle` executes the eligible stages and stops for review or revision. Never edit the frozen copies or completion artifacts. A source or frozen-plan change requires a new prepared study.
5. **Run development.** Execute the development stage and inspect its report, raw metrics, logs and limitations. `criteria_not_met` is a useful negative result. Document it; if pursuing a revised idea, write a new plan rather than changing the old result. Do not describe automated thresholds as proof or significance.
6. **Evaluate a fixed candidate.** The coordinator permits evaluation only when development meets the declared criteria. Evaluation results and config are locally visible; keep separate, newly selected evaluation seeds for each changed hypothesis, and acknowledge any data already inspected. The tool does not enforce secrecy or prevent repeated attempts.
7. **Report and decide.** Record code revision, exact configurations, controls, outcomes, deviations, failure cases and practical limits. Compare online performance and retention where relevant; do not treat oracle performance or unmatched budgets as fair superiority. Preserve negative evidence and distinguish an operational criterion from a scientific conclusion. Decide whether to stop, revise, or propose a separately specified follow-up.

Resource limits count logical generated transitions and wall time; they are not peak-memory limits or matched compute. Checksums detect ordinary accidental edits when resuming but are stored locally and can be rewritten. A partially run directory is kept for inspection and never overwritten. No agent should claim a reserved split is blind merely because this coordinator copied the config.

## Autonomous campaign

`campaign init` records the overall goal, bounded idea count and wall-time limits. `campaign run` invokes the configured Codex CLI in a separate worktree for each idea, asks it to edit the candidate model and a focused test, verifies the allowed paths and fixed controls, commits the candidate on its own branch, and runs the frozen development/evaluation workflow. It gives the next idea the results of earlier rounds and stops on infrastructure, agent, or test failure. See the toolkit README for commands and limits. The generated candidate is executable code and must be reviewed; file-scope checks and a sandbox are not an independent scientific or security audit.

Before each agent turn the campaign snapshots the local research-memory index, including linked curated observations, tentative explanations, limitations and proposed tests, plus a bounded selection of past campaign rounds. It is context for the agent, not an autonomous causal-inference system. The full snapshot remains with that round's logs. `python3 -B -m toolkit.coordinator.memory` inspects the current index; see the toolkit README for discovery and durability limits.

New campaigns run a separate read-only reviewer after a failed scorecard and, by default, after a pass. For a pass it proposes an ablation before further complexity is added. Its structured explanation and proposed controlled test are explicitly unverified and are passed to the next candidate agent; the next agent is asked to implement a discriminating test where its allowed file scope permits. Failure to produce a diagnosis is recorded rather than substituted with a fabricated result. This adds a model call per reviewed candidate and a configurable wall-time limit. An optional reported input-token threshold is checked between rounds and can be exceeded by an individual round; it is not a hard token or spending cap. A proposal is not evidence that a follow-up was run, and review of candidate code, tests and experiment results remains necessary.

`campaign init --seed-candidate <commit>` can seed a new campaign with exactly the candidate and generated-test files from a prior candidate, while retaining the current evaluator and recording the source commit and file hashes. A round may change only the generated test to investigate the seeded candidate. This is iterative code-and-experiment search, not continuous gradient training or persistence of learned weights.

New campaigns also plan one small milestone before each coding round. A separate read-only agent receives recent history and the research-memory snapshot and specifies a question, motivation, intervention, control, measurement, decision rule and limitations. Its validated JSON and prompt are saved before the coding agent starts. The coding agent is asked to address that plan within the existing candidate/test scope and disclose if it cannot. A failed or invalid planner stops the round for inspection; it does not silently invent a plan. Campaigns created before this feature retain their original behavior.

The round result and research-memory index include the milestone and an evidence status. `reported_unverified` means at least one arithmetically valid structured follow-up record was emitted; it does **not** verify that the planned intervention, measurement or decision rule was followed. `no_structured_followup` means no such record was found, not necessarily that no test was run. Read the test and logs before judging completion or scientific merit. The existing independent scorecard remains unchanged and does not automatically judge the proposed milestone. Planning adds one model call per round; its reported input usage is included in the existing between-round threshold, which remains neither a hard cap nor a cost guarantee. This remains limited to the existing binary-context candidate and test files; it is not an open-ended autonomous research scientist.
