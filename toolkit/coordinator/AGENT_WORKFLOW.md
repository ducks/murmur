# Bounded research workflow for agents

The coordinator executes a declared comparison. It does not generate a hypothesis, inspect scientific literature, modify model code, or make a scientific judgment. An agent or researcher performs those tasks and remains responsible for every claim.

1. **Choose a question.** Review `RESEARCH.md`, `EXPERIMENTS.md`, and the relevant runner. State the mechanism, what it predicts, and a result that would count against it. Check established literature when making novelty claims.
2. **Make a plan before looking at new results.** Create a versioned JSON manifest and configs. Declare the candidate, baseline, controls, metrics, target condition, measurable thresholds, and budgets. Explain controls' extra information or resources. Pick fresh seed groups and check role offsets, not just top-level seeds. A new model requires code and a registered adapter; the coordinator supports `unlabeled_context`, `candidate_context`, and `milestone_context`.
3. **Validate and commit.** Add meaningful model, causality and leakage tests; run the relevant tests in the Nix shell. Commit the plan, configs and implementation before preparing if a reconstructible revision is required. The coordinator fingerprints dirty work but does not archive it.
4. **Prepare the plan.** Run `prepare` into a new ignored directory. It copies and hashes plan/configs and captures HEAD, working-tree status and tool versions. `next` tells you the bounded next step; `cycle` executes the eligible stages and stops for review or revision. Never edit the frozen copies or completion artifacts. A source or frozen-plan change requires a new prepared study.
5. **Run development.** Execute the development stage and inspect its report, raw metrics, logs and limitations. `criteria_not_met` is a useful negative result. Document it; if pursuing a revised idea, write a new plan rather than changing the old result. Do not describe automated thresholds as proof or significance.
6. **Evaluate a fixed candidate.** The coordinator permits evaluation only when development meets the declared criteria. Evaluation results and config are locally visible; keep separate, newly selected evaluation seeds for each changed hypothesis, and acknowledge any data already inspected. The tool does not enforce secrecy or prevent repeated attempts.
7. **Report and decide.** Record code revision, exact configurations, controls, outcomes, deviations, failure cases and practical limits. Compare online performance and retention where relevant; do not treat oracle performance or unmatched budgets as fair superiority. Preserve negative evidence and distinguish an operational criterion from a scientific conclusion. Decide whether to stop, revise, or propose a separately specified follow-up.

Resource limits count logical generated transitions and wall time; they are not peak-memory limits or matched compute. Checksums detect ordinary accidental edits when resuming but are stored locally and can be rewritten. A partially run directory is kept for inspection and never overwritten. No agent should claim a reserved split is blind merely because this coordinator copied the config.

## Autonomous campaign

`campaign init` records the overall goal, bounded idea count and wall-time limits. `campaign run` invokes the configured Codex CLI in a separate worktree for each idea, asks it to edit the candidate model and a focused test, verifies the allowed paths and fixed controls, commits the candidate on its own branch, and runs the frozen development/evaluation workflow. It gives the next idea the results of earlier rounds and stops on infrastructure, agent, or test failure. See the toolkit README for commands and limits. The generated candidate is executable code and must be reviewed; file-scope checks and a sandbox are not an independent scientific or security audit.

Before each agent turn the campaign snapshots the local research-memory index, including linked curated observations, tentative explanations, limitations and proposed tests, plus a bounded selection of past campaign rounds. It is context for the agent, not an autonomous causal-inference system. The full snapshot remains with that round's logs. `python3 -B -m toolkit.coordinator.memory` inspects the current index; see the toolkit README for discovery and durability limits.

New campaigns run a separate read-only reviewer after a failed scorecard and, by default, after a pass. For a pass it proposes an ablation before further complexity is added. Its structured explanation and proposed controlled test are explicitly unverified and are passed to the next candidate agent; the next agent is asked to implement a discriminating test where its allowed file scope permits. Failure to produce a diagnosis is recorded rather than substituted with a fabricated result. This adds a model call per reviewed candidate and a configurable wall-time limit. An optional reported input-token threshold is checked between rounds and can be exceeded by an individual round; it is not a hard token or spending cap. A proposal is not evidence that a follow-up was run, and review of candidate code, tests and experiment results remains necessary.

`campaign init --seed-candidate <commit>` can seed a new campaign with exactly the candidate and generated-test files from a prior candidate, while retaining the current evaluator and recording the source commit and file hashes. A round may change only the generated test to investigate the seeded candidate. This is iterative code-and-experiment search, not continuous gradient training or persistence of learned weights.

New campaigns also plan one small milestone before each coding round. A separate read-only agent receives recent history and the research-memory snapshot and specifies a question, motivation, intervention, control, measurement, decision rule and limitations. Its validated JSON and prompt are saved before the coding agent starts. The coding agent is asked to address that plan within the existing candidate/test scope and disclose if it cannot. A failed or invalid planner stops the round for inspection; it does not silently invent a plan. Campaigns created before this feature retain their original behavior.

The round result and research-memory index include the milestone and an evidence status. `reported_unverified` means at least one arithmetically valid structured follow-up record was emitted; it does **not** verify that the planned intervention, measurement or decision rule was followed. `no_structured_followup` means no such record was found, not necessarily that no test was run. Read the test and logs before judging completion or scientific merit. The existing independent scorecard remains unchanged and does not automatically judge the proposed milestone. Planning adds one model call per round; its reported input usage is included in the existing between-round threshold, which remains neither a hard cap nor a cost guarantee. This remains limited to the existing binary-context candidate and test files; it is not an open-ended autonomous research scientist.

Milestone schema version 2 requires the planner to choose `test_only` or `model_change` and freeze exact labels for the primary reported comparison. For `test_only`, the supervisor stops and preserves the worktree if the candidate model file differs from the starting commit, both before and after tests. For `model_change`, edits are allowed but the flag requests review; the supervisor cannot tell whether the changes are necessary or isolated. It checks all retained structured records, not just the preview, for an exact match to the planned measurement and candidate/control labels. Missing primary output stops the round. A match remains unverified: labels and valid arithmetic do not prove the intervention, pairing, sample size, or decision rule. The independent reviewer is asked to check the planned scope and flag unrelated changes. Previously initialized campaigns retain their original milestone schema and behavior.

New campaigns request a structured milestone assessment from the existing separate read-only reviewer: `followed`, `partial`, `not_followed`, or `unclear`, with evidence references and deviations. The assessment is saved separately from deterministic scope and label checks, indexed into research memory, and shown to subsequent rounds. Failed, disabled, skipped, or legacy reviews appear as `unavailable`, never as a pass. This is an agent's assessment, not proof: the reviewer may misunderstand the code, overlook a problem, or make an unsupported judgment, and it does not rerun experiments. The assessment does not block subsequent rounds automatically; the agent is told to treat non-followed or unavailable assessments as unresolved. Existing campaigns retain their original reviewer schema.

For newly initialized campaigns, the primary milestone comparison also requires `MURMUR_PAIRED` JSON records in the test log: one per seed with `measure`, `candidate`, `control`, nonnegative integer `seed`, `candidate_correct`, `control_correct`, and `trials`. Labels must match the frozen primary comparison; there must be 2–10,000 unique seeds with equal positive trials and valid integer counts. The supervisor requires exactly one primary aggregate, checks that all per-seed totals match it, saves sorted records and a SHA-256 hash, and computes an independent seed-resampled percentile interval. Missing, malformed or inconsistent evidence stops the round for inspection. This version supports equal-trial binary correct-count outcomes only, and its RNG is a fixed local seed. Existing initialized campaigns retain their prior behavior.

An arithmetic check does not establish actual seed use, pairing, seed freshness, experimental protocol, independence, or scientific validity. The coding agent supplies both aggregate and seed records; they are not authenticated independent observations. The reviewer receives the check result and remains responsible for assessing the implementation. Saved per-seed records and test logs must be retained with the campaign; the hash detects later changes only when the recorded digest itself is trusted.

For newly initialized campaigns, the supervisor now allocates exactly 100 primary seed IDs and separate stream, initialization, and probe role seeds for each round. Values are deterministically derived from the campaign ID and round, checked for duplicate role seeds and overlap with that round's scorecard seed roles, and saved and hashed before the coding agent begins. The planner is told the fixed sample size; the agent receives the visible allocation and must use each row, reporting its `seed_id` in the paired record. The supervisor checks the exact set of IDs and verifies that the allocation file was unchanged through testing. This is a traceable allocation, not a hidden holdout, proof that the code used the values, or a global guarantee of freshness across historical campaigns. It assumes the three listed roles fit the primary test; if they do not, the agent must report a blocker. Existing initialized campaigns retain their original behavior.

Archived campaigns with a frozen seed allocation and paired records can be rerun locally with `python3 -B -m toolkit.coordinator.replay <archive-dir> <new-ignored-output-dir>` inside the Nix shell. The tool checks the candidate and test snapshots against their recorded Git commit, checks archived allocation and paired-record hashes, regenerates the allocation from campaign ID and round, runs the committed Rust tests in a detached worktree, and compares all primary paired records with the archive. A successful clean replay removes its worktree and isolated build cache; failures preserve them when present. The code being replayed is executable and is not sandboxed by this tool: inspect and trust it before replaying. A match demonstrates reproducibility in the replay environment, not an independently designed experiment, global seed freshness, or scientific validity. The Nix package set is unpinned.

Newly initialized campaigns automatically replay the committed primary paired test before review and before advancing to the next round. They freeze replay inputs from the candidate commit, allocation and paired records, verify their hashes, rerun the candidate tests in a detached worktree, and compare every primary seed record. The replay uses the campaign-owned build cache; its own worktree is removed after a clean match and the campaign later cleans its shared cache under the normal ownership rules. A mismatch, test failure, or unexpected worktree change stops the campaign for inspection and retains replay evidence. Replay status is included in the round and research-memory records. Previously initialized campaigns retain their original behavior.

Replay executes the same generated Rust code again without an additional sandbox or model call. It checks reproducibility, not whether the experiment was scientifically valid, whether the seeds were actually used as claimed, or whether it generalizes. It adds compute and wall time; the Nix package set is unpinned. The underlying generated candidate and tests must be trusted in the same way as the first execution.

Newly initialized campaigns record review provenance for every completed candidate: the campaign base, round-start commit, candidate commit and parent, actual round delta and hashes of the candidate/test files. When the first round transplants a seed candidate, the record separately identifies the seed source, campaign-base-to-transplant changes and hashes. It verifies the seed source contents and expected paths, checks the candidate parent and allowed paths, and saves both diffs as patches. The reviewer is directed to assess `round_start_commit` to `candidate_commit` rather than a broad diff against an older seed source. This is Git provenance, not an assessment of scientific validity. Older campaigns retain their original behavior.

A seeded test suite may emit paired records for older or secondary comparisons as well as the current primary one. The paired-evidence checker validates their record shape and count bounds but excludes them from the primary calculation; it separately reports how many non-primary records it saw. The current primary still must have exactly the allocated seed IDs, one matching aggregate and matching totals. Non-primary records are retained in the full test log but are not validated against their own aggregates by this check.
